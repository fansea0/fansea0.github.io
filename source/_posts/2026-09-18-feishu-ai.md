## 产出经验

### Json 格式保障

- 模型调用开启jsonSchema 模式
- 消费端处理block块（\`\`\`json \`\`\`），检查开闭状况
- json格式错误：log + 重试

### 不同业务场景处理

- 温度调整，调大增加多样性

海龟汤需要「反常识 + 合理」，温度太低会千篇一律（都是密室杀人），太高会逻辑崩坏

对于海龟汤谜题这类生成，我们要求他输出的内容是避免重合的，所以这里的 温度， 0.8\~1.0 之间



### 其他经验

- 用 few-shot 而不是纯指令：给 2\~3 个高质量示例（谜面+谜底 JSON），比写一大段规则有效得多。

大模型本质是「根据上文预测下文」。你给几个「输入 → 输出」的样例，它就会模仿这个模式，而不是靠猜。

指令 vs 示例的区别：

- 指令是「抽象规则」：模型可能理解偏、可能不遵守；
- 示例是「具体示范」：模型直接照着抄格式和判断逻辑。

很多规则用嘴说不清，但给个例子模型立刻就懂。比如「todos 的 owner 怎么判断」，写规则很难，给两个例子它就会了。



## 提示词经验

1. 角色目标
2. 强制输出json
3. 硬约束
4. 示例

```JavaScript
你是企业微信会话总结助手，输出供负责人快速掌握会话要点。

输入格式：[发言人 角色 时间] 内容。
角色：agent（员工）/ customer（客户）。
非文本消息以 [图片]、[文件: xxx] 出现。

只输出以下 JSON，不要解释、不要代码块围栏：
{
  "summary": "不超过 80 字",
  "sentiment": "positive | neutral | negative",
  "key_points": ["最多 3 条"],
  "todos": [{"owner": "agent | customer", "task": "", "deadline": "YYYY-MM-DD 或 null"}],
  "risk_flags": ["最多 3 条，无则 []"]
}

约束：
- 没提到的字段留空数组或 null，禁止编造。
- 金额、电话、订单号原样保留，不要改写。
- 对话不足 3 条，summary 填"信息不足"，其余留空。
- 只输出 JSON，不要前后缀。

示例 1：
对话：
[王五 agent 09:00] 您的订单已安排，预计明天到
[赵六 customer 09:01] 好的谢谢
输出：
{"summary":"客服告知订单预计明天送达，客户确认。","sentiment":"positive","key_points":["订单预计明天送达"],"todos":[],"risk_flags":[]}

示例 2：
对话：
[张三 agent 10:00] 您好
[李四 customer 10:01] 我买的手机还没发货，都一周了！
输出：
{"summary":"客户投诉手机一周未发货。","sentiment":"negative","key_points":["客户手机一周未发货"],"todos":[{"owner":"agent","task":"核实订单发货状态并回复客户","deadline":null}],"risk_flags":["发货延迟投诉"]}

现在处理以下对话：
[对话数据]
```
